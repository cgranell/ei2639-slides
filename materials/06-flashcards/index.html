Intro

Errores comunes con patrones de diseño

Conocer un patrón no es solo saber cuándo usarlo, sino también reconocer cuándo se está usando mal.

Un patrón mal usado puede ser peor que no usar ninguno: añade clases, indirección y complejidad sin aportar flexibilidad.

Los asistentes de IA generan código con patrones con mucha facilidad, pero no siempre los aplican bien.

Detectar estos errores y saber corregirlos es parte de lo que hoy significa saber programar.

Flashcards

Cada flashcard tiene tres partes:

  1. 🔍 Síntoma: un fragmento de código o una situación.
  2. ❌ ¿Qué falla?: el diagnóstico.
  3. ✅ ¿Cómo corregirlo?: la solución.

Ante cada síntoma

¿Qué patrón se intenta aplicar? ¿Qué falla? ¿Cómo lo corregirías?

Inspira en la sección Caveats de From Data to Viz, una colección de errores frecuentes en visualización de datos en la que cada tarjeta describe un error y cómo corregirlo.

Recuerda los principios

Muchos errores se explican simplemente con los principios básicos:

  • encapsula lo que varía,
  • programa a una interfaz, no a una implementación y
  • favorece la composición sobre la herencia.

Son útiles también los principios SOLID: abierto/cerrado y responsabilidad única.

Flashcard 1

Creacional · Factory Method

La fábrica con un if que no deja de crecer

🔍 Flashcard 1 · Síntoma

La aplicación de logística necesita un transporte nuevo: el tren. Cada transporte nuevo obliga a modificar esta función.

def crear_transporte(tipo):
    if tipo == "camion":
        return Camion()
    elif tipo == "barco":
        return Barco()
    elif tipo == "avion":
        return Avion()
    # ... y una rama más por cada transporte

Para reflexionar

¿Qué ocurre al añadir Tren? ¿Y diez transportes más?

❌ Flashcard 1 · ¿Qué falla?

  • No es Factory Method. Es una fábrica simple (simple factory) porque centraliza la creación, pero no es un Factory Method según (Gamma et al. 1994).
  • Vulnera el principio abierto/cerrado. Cada tipo nuevo obliga a modificar la función, en lugar de extenderla.
  • Acopla la función a todas las clases concretas. crear_transporte() debe conocer Camion, Barco, Avion, Tren…
  • Tiende a replicarse. El mismo if tipo == ... acaba apareciendo en otras partes del código (costes, tiempos de entrega…).

Pero…

Una fábrica simple no es un error en sí misma si los tipos son pocos y casi nunca cambian. El error es confundirla con Factory Method o dejar que crezca sin control.

✅ Flashcard 1 · ¿Cómo corregirlo?

Opción 1: Factory Method

Cada subclase decide qué transporte crear.

class Logistica(ABC):
    @abstractmethod
    def crear_transporte(self) -> Transporte: ...

    def planificar_entrega(self, carga):
        t = self.crear_transporte()
        t.entregar(carga)

class LogisticaTerrestre(Logistica):
    def crear_transporte(self):
        return Camion()

class LogisticaFerroviaria(Logistica):
    def crear_transporte(self):
        return Tren()

Opción 2: registro de tipos

Un diccionario sustituye a la cadena de if.

TRANSPORTES = {
    "camion": Camion,
    "barco": Barco,
    "avion": Avion,
}

def crear_transporte(tipo):
    return TRANSPORTES[tipo]()

# Añadir el tren: una línea,
# sin tocar crear_transporte()
TRANSPORTES["tren"] = Tren

Para recordar

Añadir un tipo nuevo debería consistir en añadir código, no en modificar el que ya funciona.

Flashcard 10

Estructural · Decorator

El decorador que cambia la interfaz

🔍 Flashcard 10 · Síntoma

Tras envolver el notificador de correo con el de SMS, enviar() no manda nada.

class Notificador:
    def enviar(self, msg): ...

class NotificadorSMS(Notificador):
    def __init__(self, envuelto):
        self.envuelto = envuelto
    def enviar_sms(self, msg, telefono):   # método nuevo
        ...

n = NotificadorSMS(NotificadorEmail())
n.enviar("Hola")                         # ¿qué se envía?

Para reflexionar

¿Qué método se ejecuta en la última línea?

❌ Flashcard 10 · ¿Qué falla?

  • No redefine enviar(). Hereda el método vacío de Notificador y no delega en el objeto envuelto: el correo nunca se envía.
  • Añade una interfaz nueva. Para enviar el SMS, el cliente tiene que llamar a enviar_sms(), así que debe conocer la clase concreta del decorador.
  • Deja de ser transparente. Un decorador debería poder usarse exactamente igual que el objeto que envuelve.
  • No se pueden apilar decoradores. NotificadorSlack(NotificadorSMS(...)) no sabría que tiene que llamar a enviar_sms().

Principio vulnerado

Programa a una interfaz, no a una implementación: el cliente acaba dependiendo de NotificadorSMS, no de Notificador.

✅ Flashcard 10 · ¿Cómo corregirlo?

Misma interfaz, más comportamiento, y delegación

class NotificadorSMS(Notificador):
    def __init__(self, envuelto, telefono):
        self.envuelto = envuelto
        self.telefono = telefono   # dato extra

    def enviar(self, msg):
        self.envuelto.enviar(msg)  # delega
        self._enviar_sms(msg)      # añade

Ahora sí se pueden apilar

n = NotificadorSlack(
        NotificadorSMS(
            NotificadorEmail(),
            "600 000 000"))

n.enviar("Hola")
# correo + SMS + Slack

Para recordar

Los datos extra se pasan en el constructor, no en métodos nuevos. Y si lo que necesitas es cambiar la interfaz, no buscas un Decorator, sino un Adapter.

Flashcard 11

Estructural · Facade

La fachada que lo hace todo

🔍 Flashcard 11 · Síntoma

Cualquier cambio en la tienda en línea acaba tocando esta clase, y todo el equipo la modifica a la vez.

class FachadaTienda:
    def anadir_al_carrito(self, usuario, producto): ...
    def aplicar_descuento(self, carrito, codigo): ...
    def cobrar(self, pedido, tarjeta): ...
    def calcular_iva(self, pedido, pais): ...
    def programar_envio(self, pedido): ...
    def generar_factura_pdf(self, pedido): ...
    def registrar_usuario(self, datos): ...
    def informe_ventas_mensual(self, mes): ...
    # ... y 52 métodos más

Para reflexionar

¿Cuántas razones distintas para cambiar tiene esta clase?

❌ Flashcard 11 · ¿Qué falla?

  • Es un objeto dios (God object). La fachada concentra carritos, pagos, impuestos, envíos, usuarios e informes.
  • Vulnera el principio de responsabilidad única. La clase tiene muchas razones distintas para cambiar.
  • Contiene lógica, no solo coordinación. Métodos como calcular_iva() implementan reglas de negocio que deberían vivir en el subsistema.
  • Se convierte en un cuello de botella. Todo el equipo modifica el mismo archivo, con conflictos constantes al integrar cambios.

Un riesgo compartido

Lo mismo le puede ocurrir a un Mediator: un mediador que lo sabe todo y lo hace todo es otro objeto dios.

✅ Flashcard 11 · ¿Cómo corregirlo?

  • Varias fachadas pequeñas, una por subsistema o caso de uso: FachadaPedidos, FachadaUsuarios, FachadaInformes…
  • La fachada solo coordina y delega. La lógica de negocio vive en el subsistema.
  • Una fachada puede componer otras fachadas si hace falta.
class FachadaPedidos:
    def __init__(self, carrito, pagos, envios):
        self.carrito = carrito
        self.pagos = pagos
        self.envios = envios

    def comprar(self, usuario):
        pedido = self.carrito.cerrar(usuario)
        self.pagos.cobrar(pedido)
        self.envios.programar(pedido)
        return pedido

Para recordar

Una fachada simplifica el acceso a un subsistema; no lo sustituye.

Flashcard 20

Comportamiento · Strategy

La estrategia con el if escondido

🔍 Flashcard 20 · Síntoma

Se han creado clases para cada estrategia, pero añadir el modo “patinete” sigue obligando a modificar Navegador.

class Navegador:
    def calcular_ruta(self, origen, destino, modo):
        if modo == "coche":
            self.estrategia = RutaCoche()
        elif modo == "pie":
            self.estrategia = RutaAPie()
        elif modo == "bici":
            self.estrategia = RutaBici()
        return self.estrategia.calcular(origen, destino)

Para reflexionar

¿Qué ha ganado el diseño al crear las clases RutaCoche, RutaAPie y RutaBici?

❌ Flashcard 20 · ¿Qué falla?

  • El contexto elige la estrategia con condicionales. Navegador conoce todas las estrategias concretas.
  • Vulnera el principio abierto/cerrado. Cada modo nuevo obliga a modificar Navegador.
  • Vulnera programa a una interfaz. El contexto debería depender solo de la interfaz común de las estrategias, no de sus clases.
  • Se pierde el beneficio del patrón. El if sigue ahí, solo que más escondido.

Pero…

Elegir una estrategia a partir de un dato (un texto, una opción de configuración) no está prohibido. Lo importante es hacerlo una sola vez y fuera del contexto.

✅ Flashcard 20 · ¿Cómo corregirlo?

El contexto solo delega

class Navegador:
    def __init__(self, estrategia):
        self.estrategia = estrategia

    def calcular_ruta(self, origen, destino):
        return self.estrategia.calcular(
            origen, destino)

El cliente elige, en un único lugar

ESTRATEGIAS = {
    "coche": RutaCoche,
    "pie": RutaAPie,
    "bici": RutaBici,
    "patinete": RutaPatinete,  # nueva
}

nav = Navegador(ESTRATEGIAS[modo]())
nav.calcular_ruta(origen, destino)

nav.estrategia = RutaAPie()  # cambio en
                             # ejecución

Para recordar

El contexto no debe saber qué estrategia usa; solo que tiene una.

Flashcard 21

Comportamiento · Template Method

La subclase que se salta la plantilla

🔍 Flashcard 21 · Síntoma

Los informes rápidos salen vacíos: nunca se cargan los datos.

class Informe:
    def generar(self):            # método plantilla
        self.cargar_datos()
        self.analizar()
        self.exportar()


class InformeRapido(Informe):
    def generar(self):            # redefine la plantilla entera
        self.exportar()

Para reflexionar

InformeRapido solo quería saltarse el análisis. ¿Qué ha perdido por el camino?

❌ Flashcard 21 · ¿Qué falla?

  • La subclase redefine el método plantilla, en lugar de redefinir solo alguno de sus pasos.
  • Rompe el esqueleto del algoritmo. Desaparecen pasos obligatorios, como cargar_datos(), que la superclase debía garantizar.
  • Invierte el control. En Template Method, la superclase llama a las subclases, y no al revés: es el principio de Hollywood (“no nos llames, ya te llamaremos”).
  • Vulnera el principio abierto/cerrado. La plantilla debería estar cerrada a modificaciones y abierta a extensiones a través de sus pasos.

Pero…

Si una subclase necesita un algoritmo completamente distinto, quizá el patrón adecuado no es Template Method, sino Strategy.

✅ Flashcard 21 · ¿Cómo corregirlo?

Plantilla protegida y un gancho (hook)

from typing import final

class Informe:
    @final
    def generar(self):
        self.cargar_datos()
        if self.necesita_analisis():  # gancho
            self.analizar()
        self.exportar()

    def necesita_analisis(self):
        return True                   # por defecto

La subclase solo ajusta un paso

class InformeRapido(Informe):
    def necesita_analisis(self):
        return False

En Java, el método plantilla se declara final. En Python, @final lo comprueban herramientas como mypy.

Para recordar

Las subclases rellenan huecos de la plantilla; no la reescriben.
